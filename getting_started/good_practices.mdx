遵循以下准则，无论是建立数百篇文档的初创项目，还是扩展到千万级数据的企业级系统，都能最大化发挥 Meilisearch 的性能潜力。

## 文档格式规范 (Document formatting)

### 保持简单、统一的字段结构

Meilisearch 完全能够处理多层嵌套的复杂 JSON，你不需要手动将所有属性扁平化。然而，结构越简单，后续的搜索过滤配置就越轻松。最关键的黄金法则是：**切勿使用动态字段名（Dynamic field names）**。同一个索引内的每篇文档都应该共享相同的字段名体系。如果文档之间的字段名各不相同，Meilisearch 将无法构建有效的倒排索引。

✅ **推荐做法**：字段名统一规范，嵌套对象同样支持良好：

```json
{
  "id": 1,
  "title": "跑步鞋",
  "brand": "耐克",
  "price": 120,
  "details": {
    "color": "黑色",
    "size": 42
  }
}
```

❌ **错误做法**：动态键名（字段 Key 随着文档内容变化）：

```json
[
  {
    "id": 1,
    "Nike": { "price": 120 }
  },
  {
    "id": 2,
    "Adidas": { "price": 95 }
  }
]
```

### 使用具有明确业务意义的主键 (Primary key)

选择能够全局唯一标识每篇文档且长期保持稳定的字段作为主键。如果文档来源于数据库，直接使用数据库自增 ID 或 UUID 即可。如果 Meilisearch 未能在首批文档中推断出合适的主键候选字段，它会提示你显式指定。

### 剔除无用冗余字段

如果某个字段既不需要参与全文搜索（Searchable）、也不需要作为过滤（Filterable）或排序条件（Sortable），甚至前端展示时也不会用到，请在写入 Meilisearch 之前直接将其剔除。文档越小，建索速度越快，占用的磁盘和内存开销也越少。

## 长文本分块 (Chunking content)

在为文章、长篇开发文档、电子书或博客等长文本建立索引时，**建议将其拆分成更小、更具体的逻辑分块（Chunks）**，而不是把整整几万字的长页面作为一个单篇文档存入。

### 为什么要进行内容分块？

- **显著提升相关度得分**：用户搜索“安装教程”时，命中一个专注于安装的 200 字小章节，远比命中一篇包含 5000 字全集的大页面要精准得多。
- **更好的前端展示体验**：搜索结果中可以直接高亮呈现精准的定位摘要，而不是铺天盖地的大段文字。
- **更快的建索速度**：小颗粒度的文档在分词和倒排索引构建时的并行处理效率更高。

### 如何科学分块？

按照标题（Headings）、小节（Sections）或自然段落等逻辑边界进行切分。每个分块应当具备一定的自包含性，即使脱离上下文也能被读者理解：

```json
[
  {
    "id": "getting-started-install",
    "page": "快速上手",
    "section": "环境安装",
    "content": "使用以下命令快速安装 Meilisearch...",
    "url": "/docs/getting-started#installation"
  },
  {
    "id": "getting-started-config",
    "page": "快速上手",
    "section": "参数配置",
    "content": "通过设置环境变量来配置你的实例参数...",
    "url": "/docs/getting-started#configuration"
  }
]
```

务必附带页面标题、小节锚点与跳转 URL 等元数据字段，方便用户点击搜索结果时直接精确定位到原网页。

## 批量请求与网络优化 (Batching requests)

### 使用大批量（Batch）导入文档

发送单次大体积的 HTTP 请求，处理效率远高于连续发送多次小请求。例如，将 10 万篇文档分成两批（每批 5 万篇）导入，耗时远少于分成四批（每批 2.5 万篇）。

默认情况下，Meilisearch 允许单次请求体（Payload）最大达 **100MB**（企业版支持调大）。

### 开启 HTTP 请求压缩

在发送大量数据时，使用 `gzip`、`deflate` 或 `br`（Brotli）对 HTTP 请求体进行压缩，能极大降低网络传输耗时和服务器带宽压力。Meilisearch 原生支持所有主流的 [压缩编码规范](/reference/api/headers)。

### 异步轮询任务执行状态

向 Meilisearch 推送多批数据时，你**不需要**苦苦等待上一批任务执行完毕才发下一批。Meilisearch 的底层任务队列（Task Queue）会自动将请求排队并按序消费。你可以异步查询 [任务状态 (Task Status)](/capabilities/indexing/tasks_and_batches/monitor_tasks)，以便在发生网络异常或格式错误时及时捕获告警。

## 索引构建性能调优 (Indexing performance)

### 务必“先配置设置，后写入文档”

在向索引写入大量文档**之前**，务必先完成索引的核心配置（排序规则 rankingRules、过滤字段 filterableAttributes、搜索字段 searchableAttributes）。如果在写入了数百万文档后再去修改设置，Meilisearch 将不得不触发全量文档的底层重建索引，极耗 CPU 与磁盘 I/O。

```bash
# 步骤 1: 创建索引并提前配置好规则
curl -X PATCH 'MEILISEARCH_URL/indexes/movies/settings' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer API_KEY' \
  --data-binary '{
    "searchableAttributes": ["title", "overview"],
    "filterableAttributes": ["genre", "release_year"],
    "sortableAttributes": ["release_year", "rating"]
  }'

# 步骤 2: 然后再批量导入数据集
curl -X POST 'MEILISEARCH_URL/indexes/movies/documents' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer API_KEY' \
  --data-binary @movies.json
```

### 严格收窄可搜索属性 (Searchable attributes)

默认情况下，文档中的所有字段都是可被检索的。强烈建议将其限定为仅用户真正会去搜索的字段（例如标题、正文、标签）。这不仅能极大提升相关度质量，还能缩减索引体积、加快建索速度。

### 多语言内容使用独立索引

如果你的业务数据集包含多种不同语言（如中文、英文、日语），请为每种语言创建单独的索引。Meilisearch 的分词器（Tokenizer）、停用词典和排序算法针对不同语言有专门优化，混在一个索引中会导致各种语言的分词精度均受折损。

### 避免创建过多无意义的索引

每个索引都会占用系统的内存映射和文件句柄资源。如果你在多索引并发联合搜索时观察到性能瓶颈，应优先考虑在逻辑上合并索引，改用字段过滤器进行区分。

### 大规模向量检索启用二进制量化 (Binary Quantization)

如果你正在使用 AI 向量搜索，且文档数量超过 100 万篇、向量维度较高（1400 维以上），建议开启 [二进制量化 (Binary Quantization)](/reference/api/settings/update-embedders)。它会在极轻微折损语义精度的前提下，将向量体积压缩 10 倍以上，显著释放内存压力并加快检索速度。

<Warning>
二进制量化是不可逆的操作。一旦开启，若想还原为原本的浮点向量精度，必须对整个索引重新跑模型生成向量。
</Warning>

## 保持引擎版本及时升级

Meilisearch 的每次新版本发布通常都会包含针对分词性能、内存管理和向量算法的实质性提升。建议定期关注 [更新日志](/changelog) 以及 [GitHub Releases](https://github.com/meilisearch/meilisearch/releases?q=prerelease%3Afalse)。
