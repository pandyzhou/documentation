`_rankingScore` 是一个介于 `0.0` 到 `1.0` 之间的归一化浮点数值，代表该文档与当前查询词的契合程度。`1.0` 代表完美匹配，越接近 `0.0` 代表匹配度越低。默认情况下 Meilisearch 不会返回该分值，需要客户端显式声明索取。

## 请求返回打分

在搜索请求体中将 `showRankingScore` 设为 `true`：

<CodeGroup>

```sh
curl \
  -X POST 'MEILISEARCH_URL/indexes/movies/search' \
  -H 'Content-Type: application/json' \
  --data-binary '{
    "q": "batman dark knight",
    "showRankingScore": true
  }'
```

</CodeGroup>

响应中的每篇命中结果都会包含 `_rankingScore` 字段：

<CodeGroup>

```json
{
  "hits": [
    {
      "id": 155,
      "title": "The Dark Knight",
      "_rankingScore": 0.9546
    },
    {
      "id": 36657,
      "title": "Batman Begins",
      "_rankingScore": 0.8103
    }
  ],
  "query": "batman dark knight"
}
```

</CodeGroup>

## 请求深度打分拆解明细

若想深入洞察文档为什么得到该分数，可同时将 `showRankingScoreDetails` 设为 `true`。响应中将为每篇文档追加一个 `_rankingScoreDetails` 对象，展示各项生效的排序规则分别贡献了多少分：

<CodeGroup>

```sh
curl \
  -X POST 'MEILISEARCH_URL/indexes/movies/search' \
  -H 'Content-Type: application/json' \
  --data-binary '{
    "q": "batman dark knight",
    "showRankingScore": true,
    "showRankingScoreDetails": true
  }'
```

</CodeGroup>

返回数据结构如下：

<CodeGroup>

```json
{
  "hits": [
    {
      "id": 155,
      "title": "The Dark Knight",
      "_rankingScore": 0.9546,
      "_rankingScoreDetails": {
        "words": { "order": 0, "matchingWords": 3, "maxMatchingWords": 3, "score": 1.0 },
        "typo": { "order": 1, "typoCount": 0, "maxTypoCount": 3, "score": 1.0 },
        "proximity": { "order": 2, "score": 0.9286 },
        "attributeRank": { "order": 3, "attributeRankingOrderScore": 1.0, "score": 1.0 },
        "exactness": { "order": 5, "matchType": "noExactMatch", "score": 0.3333 }
      }
    }
  ]
}
```

</CodeGroup>

`_rankingScoreDetails` 中的每个 Key 对应一条[排序规则](/capabilities/full_text_search/relevancy/ranking_rules)，内部的 `score` 反映了该文档在该规则下的具体得分。

## 得分是如何计算出来的？

排序规则要么根据文本相关度排序（`words`, `typo`, `proximity`, `exactness`, `attributeRank`, `wordPosition`），要么根据字段的字面数值排序（`sort`）。由于 `sort` 并非衡量语义相关度，因此它**不参与** `_rankingScore` 的加权计算。

Meilisearch 根据排序规则列表的排列顺序，按层级赋权合并各项子规则的分数。排在越靠前位置的规则，权重比率越大。

<Note>
文档的得分是绝对独立的，不会因为同一索引中其他文档的得分变动而改变。

例如，文档 A 针对特定查询词得分 `0.5`，无论文档 B、C 考了 0 分还是满分，A 的分数都不会发生漂移。
</Note>

## 哪些索引设置会影响得分？

下表列出了所有能够直接影响 `_rankingScore` 的索引配置项。**未列出的其他设置均不影响该打分。**

| 索引配置项 | 触发影响的条件 | 影响原因 |
| :--- | :--- | :--- |
| `searchableAttributes` | 启用了 `attributeRank` 规则时 | 决定了命中文档出现在哪个字段时的权重高低 |
| `searchableAttributes` | 启用了 `wordPosition` 规则时 | 决定了关键词出现在字段头部还是尾部的打分 |
| `rankingRules` | 始终生效 | 各条规则在数组中的顺序直接决定了该规则的加权比率 |
| `stopWords` | 始终生效 | 停用词直接影响 `words` 规则对关键词总数的统计 |
| `synonyms` | 始终生效 | 同义词直接影响 `words` 规则的匹配判定 |
| `typoTolerance` | 启用了 `typo` 规则时 | 决定了允许容忍的最大编辑距离阈值 |

## 业务应用场景

- **精准调试相关度**：使用 `showRankingScoreDetails` 穿透排查为什么某条文档没排到第一位，指导调优排序规则或字段权重。
- **打造置信度 UI 徽标**：在前端展示相关度百分比进度条（如“匹配度 95%”），直观反映可信度。
- **低质量兜底拦截**：前端可过滤掉得分低于设定阈值（例如 `0.4`）的弱相关内容。
- **A/B 测试科学评估**：对比不同规则配置下的打分表现，量化评估搜索质量改进。
