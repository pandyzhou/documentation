Meilisearch 通过 [`semanticRatio` 参数](/capabilities/hybrid_search/advanced/custom_hybrid_ranking) 提供了三种不同的搜索模式：纯关键词搜索、纯语义搜索与混合搜索。每种模式在不同数据类型与用户习惯下各有优劣。

本文帮助你权衡利弊，为你的业务挑选最适合的技术路线。

## 三种搜索模式对比

`semanticRatio` 参数用于精确控制 Meilisearch 如何调配关键词与向量权重的融合比例：

| 搜索模式 | `semanticRatio` 取值 | 工作机制 |
| :--- | :--- | :--- |
| **纯关键词搜索** | `0.0` | 仅使用[全文检索 (Full-text)](/capabilities/full_text_search/overview)。结果必须包含查询词（或相近错别字）。完全不调用向量模型。 |
| **混合搜索 (Hybrid)** | `0.0 < ratio < 1.0` | 同时并发运行关键词与语义检索并融合结果。数值越小越偏向关键词，数值越大越偏向语义理解。 |
| **纯语义搜索** | `1.0` | 仅依靠向量余弦相似度。结果严格根据文档向量与查询词向量在高维空间中的距离进行排序。 |

## 各模式适用场景决策

### 1. 纯关键词搜索 (`semanticRatio = 0`)

**最适合以下场景**：
- 用户搜索明确的产品型号、商品 SKU、订单号或唯一编号
- 包含高度专业化固定术语的结构化数据集（如法律文书、医疗处方记录、代码库）
- 需要高度可预测、确定性且易于解释的检索结果
- 希望规避为查询词临时生成向量所带来的网络调用延迟

**典型示例**：
- `"iPhone 15 Pro Max 256GB"`
- `"错误码 0x80070005"`
- `"Python requests.exceptions.ConnectionError"`

### 2. 纯语义搜索 (`semanticRatio = 1`)

**最适合以下场景**：
- 用户习惯用长句自然语言描述诉求，而不是具体的固定词汇
- 内容类型高度同质（全是商品详情描述、全是知识问答对 Q&A）
- 存在严重的用词不一致痛点（如用户搜“电脑”，而数据库里只写了“笔记本”或“PC”）
- 构建[智能体对话搜索 (Agentic search)](/capabilities/agentic_search/overview)或基于 RAG 的智能问答

**典型示例**：
- `"办公桌上用来给咖啡保温的小东西"`
- `"厨房水龙头漏水怎么修"`
- `"适合站立工作一整天穿的舒服鞋子"`

### 3. 混合搜索 (`0 < semanticRatio < 1`)

**最适合以下场景**：
- 用户的搜索习惯千差万别，常常将精准词汇与口语描述混合在一起
- 数据集包含多元丰富的内容类型
- 既想牢牢抓住精确命中的爆款，又不想漏掉含义相关的潜在推荐
- 电商商城搜索、技术知识库搜索、多板块社区论坛检索

**典型示例**：
- `"无线人体工学键盘"`（关键词“无线” + 语义“人体工学舒适度”）
- `"Python 异步数据库连接池"`（技术术语 + 概念功能）
- `"50元以内的红色夏季连衣裙"`（属性参数 + 风格描述）

## 核心权衡要素

### 响应延迟 (Latency)

| 模式 | 相对延迟表现 | 说明 |
| :--- | :--- | :--- |
| **纯关键词搜索** | **最快（通常 <10ms）** | 纯倒排索引扫描，无需调用任何向量计算 |
| **纯语义搜索** | **中等（约 30~80ms）** | 需要在收到请求时实时调用嵌入模型将查询词转化为向量 |
| **混合搜索** | **相对最耗时（约 40~90ms）** | 底层并发执行两路检索，随后执行融合打分算法 |

延迟的差异主要取决于嵌入器的类型。云端 API（OpenAI, Cohere）会增加外网网络往返耗时；而本地部署的 Embedder（HuggingFace, Ollama）虽然免去了外网延迟，但会占用服务器本地的 CPU/GPU 算力。

### 词汇不匹配（同义词鸿沟）处理

这正是语义搜索的最大价值所在。以厨具数据集为例：

| 用户查询词 | 纯关键词搜索召回情况 | 纯语义搜索召回情况 |
| :--- | :--- | :--- |
| `"锅铲"` | 仅返回包含“锅铲”的文档 | 返回锅铲、炒菜铲、牛排夹、料理木勺等相关工具 |
| `"煎薄饼用的工具"` | 结果几乎为空（搜不到） | 精准推荐不粘锅平底锅、薄饼翻铲 |
| `"苏泊尔 CFXB40FC833"` | 精准召回该唯一型号 | 可能会推测推荐其他类似电饭煲，失去唯一精准性 |

混合搜索完美平衡了以上矛盾：它既能精准命中 `苏泊尔 CFXB40FC833`，又能在用户搜口语“翻煎饼工具”时准确推送锅铲。

## 初始权重参数推荐指南

| 具体业务场景 | 推荐 `semanticRatio` | 业务考量依据 |
| :--- | :--- | :--- |
| **电商商城商品搜索** | `0.5` 到 `0.7` | 用户既搜品牌型号，又搜风格痛点 |
| **技术开发文档与知识库** | `0.5` 到 `0.8` | 自然语言问句与技术 API 兼备 |
| **源码搜索 / 编程代码库** | `0.0` 到 `0.3` | 代码对变量名和符号精确匹配要求极高 |
| **客服问答 / 工单系统** | `0.7` 到 `1.0` | 用户多使用口语长句描述故障 |
| **工业零件号 / SKU 目录** | `0.0` 到 `0.3` | 精确编号不允许模糊语义替代 |
| **社区论坛 / 动态博客** | `0.5` 到 `0.7` | 兼顾话题标签与长篇动态内容 |

## 何时**不应**使用混合搜索？

- **纯图片视觉搜索**：如果数据只有图片没有文字元数据，关键词搜索无从下手，应直接使用基于多模态的纯语义检索。
- **纯粹的“相似推荐”场景**：使用 [`/similar` 接口](/capabilities/personalization/getting_started/recommendations) 寻找关联文档时，底层已是纯向量余弦计算，无需混合检索。
