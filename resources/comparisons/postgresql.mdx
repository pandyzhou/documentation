PostgreSQL 通过其内置的 `tsvector` 与 `tsquery` 数据类型提供了原生的全文检索能力，并通过 [pgvector](https://github.com/pgvector/pgvector) 扩展支持了向量相似度检索。对于简单的内部业务场景，这无疑非常便利；但对于面向最终用户的交互式搜索体验，通用关系型数据库与专业搜索引擎之间存在显著的差距。

本文全面对比这两种方案：首先对比 PostgreSQL 全文检索（FTS），随后对比 [基于 pgvector 的向量与混合搜索](#vector-and-hybrid-search-pgvector)。

## 核心维度速查表

| 对比维度 | Meilisearch | PostgreSQL FTS 原生检索 |
| :--- | :---: | :---: |
| **主要定位** | 专用全文与向量搜索引擎 | 通用关系型数据库 |
| **错别字容错** | 原生内置（Levenshtein 编辑距离） | 需额外安装 `pg_trgm` 扩展 |
| **分面统计 (Facets)** | 原生一流 API 支持，毫秒级响应 | 实现极其复杂，高并发下拖垮数据库 |
| **中文及多语言分词** | CJK 中日韩原生深度优化分词 | 极有限（原生无中文词库，需装第三方扩展） |
| **打字即搜响应** | 深度优化至 50 毫秒以内 | 架构非为此场景设计 |
| **相关度规则调优** | 多维度排序流水线灵活定制 | 仅提供基础粗糙的 `ts_rank` |
| **前端组件生态** | 与 InstantSearch 完美兼容 | 零前端生态 |

## PostgreSQL 全文检索（FTS）的固有优势

### 1. 单系统架构极简
将搜索留在现有的 PostgreSQL 数据库中，意味着无需搭建和运维额外的独立基础设施。对于简单的后台查询，这大幅降低了架构与运维复杂度。

### 2. 强事务一致性 (ACID)
搜索结果与业务数据天然在同一个事务中提交，彻底消除了数据库与独立搜索引擎之间的网络双写延迟和数据不一致痛点。

### 3. 原生 SQL 表达力
可以在单条 SQL 语句中将全文检索与普通多表 JOIN、复杂的聚合 GROUP BY 结合在一起。

## 什么时候必须选用 Meilisearch？

### 1. 你需要拼写容错（Typo-tolerance）
PostgreSQL 默认全文搜索无法处理错别字。虽然 `pg_trgm` 能做三元模糊匹配，但缺乏对词距和智能拼写容错的感知。Meilisearch 全自动处理错字，并允许针对字段单独设定容错阈值。

### 2. 你需要电商级分面筛选与统计
在 PostgreSQL 中实现分面导航极其消耗算力，尤其是同时统计多个分类维度的分布数量时。Meilisearch 提供了专用的底层位图索引，专为分面筛选毫秒级响应而生。

### 3. 你需要极致流畅的“打字即搜”体验
PostgreSQL 并非为亚 50ms 的即时打字感知而设计。在海量数据集上频繁进行模糊全文打分，会快速耗尽数据库连接池与 CPU。

### 4. 你的用户使用非拉丁语系（如中文）
PostgreSQL 官方不自带中文、日文、韩文的分词字典。Meilisearch 底层分词器原生针对中日韩文本进行了深度的连续切词优化。

### 5. 你需要面向公众的前端搜索接口
Meilisearch 提供开箱即用的安全 REST API，支持多级 API 密钥和针对多租户的租户令牌（Tenant Tokens）。直接将 PostgreSQL 暴露给公网具有极大的安全隐患。

### 6. 避免搜索影响核心业务数据库性能
在大型业务库上跑繁重的模糊全文检索，会直接与主业务事务（如下单、支付、用户登录）争抢 CPU 和内存资源。独立的搜索引擎支持完全解耦、水平弹性扩缩容。

## 向量与混合搜索深度较量：Meilisearch vs pgvector

pgvector 扩展为 PostgreSQL 添加了 `vector` 向量数据类型、空间距离比较符以及可选的近似最近邻（ANN）索引。然而，**pgvector 仅仅是一个向量存储与查询层，它不是一个搜索引擎**：所有将裸向量转化为真实搜索体验的脏活累活（向量生成、混合检索打分融合、重排序、带过滤条件的向量搜索），都必须由你在业务代码里手写搭建。而 Meilisearch 开箱即带全套能力。

| 核心特性 | Meilisearch | pgvector |
| :--- | :---: | :---: |
| **向量生成流水线** | 内置嵌入器（OpenAI, Cohere, Ollama 等）自动计算 | 必须在应用层自己写代码调用外部模型 |
| **混合搜索融合** | 单个请求，引擎内部自适应智能融合 | 必须发两次请求，在业务层手动算融合算法 |
| **打分融合算法** | 绝对相关度归一化得分 (0 到 1) | 基于位次的倒数排名融合（RRF） |
| **索引与检索算法** | 磁盘优化的 ANN（基于 HNSW 的 Hannoy 引擎） | 默认暴力 KNN，可选 HNSW/IVFFlat |
| **带过滤条件的向量搜索**| 原生深度集成，过滤与向量并发结合 | 先索引扫描后过滤，极易导致候选集急剧缩水 |
| **向量量化压缩** | 单配置一键开启 1-bit 二进制量化 | `halfvec`、二进制或稀疏向量（需改表结构） |
| **向量维度上限** | 无硬性限制（3000+ 维平稳运行） | 2000 维 (全精度), 4000 维 (halfvec) |

### 1. 向量生成流水线：开箱即用 vs 全套自研
使用 pgvector 时，生成向量完全是你的责任：批量打包、网络重试、API Key 管理、Token 计费以及用户查询时的实时转向量，全部要写在业务代码里。这是一套必须长期维护监控的沉重包袱。

在 Meilisearch 中，你只需声明一个嵌入器（如 OpenAI 或本地 Ollama），Meilisearch 在建索和用户搜索时**全自动向模型发起调用并缓存向量**。切换模型只需改一行配置，无需重写一行代码。

### 2. 混合搜索：单次查询 vs 两路自写融合
在 pgvector 中做混合搜索，你必须先查一次全文索引，再查一次向量索引，然后在应用层用复杂的 SQL CTE 或 Python 脚本手动写 RRF 算法将两份列表合并。

在 Meilisearch 中，混合搜索就是一句带 `hybrid: { semanticRatio, embedder }` 的普通请求，融合逻辑在引擎底层高效完成。

### 3. 为什么带过滤条件的向量搜索在 pgvector 中极易翻车？
在 pgvector 的 HNSW 索引上使用 `WHERE` 过滤时，**过滤器是在向量扫描之后生效的**。如果一个过滤条件筛掉了 90% 的行，在默认的探查深度下，最终返回的候选结果可能只剩下寥寥几条，造成严重的“召回率断崖式下跌”。

而在 Meilisearch 中，过滤引擎与向量引擎深度互通。如果过滤后的候选集较小，底层 Hannoy 会自动自适应切换为精准遍历，确保在任何复杂 Filter 下都能返回满额的高质量结果。

## 什么时候用 pgvector 就足够了？
- 你需要 100% 召回率的暴力最近邻检索（Brute-force KNN）
- 你的业务已经维护了成熟的 Python 算法流水线，向量搜索纯粹作为离线内部系统使用，无需对外提供毫秒级交互体验
- 你坚持所有数据必须在强 ACID 事务内与关系表严格捆绑

## 什么时候用 PostgreSQL 原生全文检索就足够了？
- **数据规模较小（数千到数万行），并发搜索量极低**
- **搜索仅面向管理后台人员内部查阅，无需拼写容错与高亮展示**
- **无法增加任何独立容器或额外运维开销**
